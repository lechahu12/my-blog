# webapp-blog

이 스킬은 `my-blog` 저장소의 "웹앱 하나 추가" 작업 하네스다. `CLAUDE.md`에 정의된 프로젝트 규칙을 실행 가능한 절차로 풀어놓은 것이므로, 이 스킬을 따르면 곧 `CLAUDE.md`를 따르는 것과 같다. 둘이 어긋나면 저장소에 있는 `CLAUDE.md`가 최종 권위를 가진다 — 이 스킬이 오래되어 못 따라간 부분이 있을 수 있으니 그럴 땐 `CLAUDE.md`를 우선하고, 가능하면 이 스킬도 같이 갱신해줄 것을 사용자에게 제안한다.

핵심 원칙: **웹앱 하나 = 서브에이전트 4번(Plan/Build/Review는 서브에이전트, Embed는 직접) + 승인 게이트 1번.** 절대 사용자 승인 없이 Build 단계로 넘어가지 않는다. 막히면 바로 사용자에게 알린다.

## 0. 시작 전에

사용자가 만들고 싶은 웹앱의 주제/아이디어를 명확히 하지 않았다면 먼저 구체화한다 (어떤 기능, 어떤 느낌인지). 이미 충분히 구체적이면 바로 Plan 단계로 진행해도 된다 — 매번 긴 인터뷰를 할 필요는 없다.

이 문서의 `{{APP_SLUG}}`는 폴더명으로 쓸 영문 kebab-case 이름(예: `pomodoro-timer`), `{{APP_NAME}}`은 사용자에게 보여줄 한글 이름(예: "포모도로 타이머")이다.

## 1. Plan — 계획 수립 (서브에이전트, 승인 필요)

Agent 도구로 계획용 서브에이전트를 하나 띄운다. 이 서브에이전트에게 `assets/spec-template.md`를 읽게 하고, 그 구조를 그대로 채워 저장소 루트에 `spec.md`로 저장하도록 지시한다 (기존 `spec.md`가 있다면 이전 앱의 계획이므로 덮어써도 된다 — 과거 내용이 필요하면 미리 git log로 확인 가능하다고 안내).

Plan 서브에이전트에게 반드시 전달할 내용:
- 만들 웹앱 주제, 원하는 핵심 기능, 사용자가 언급한 제약사항
- 저장소의 기존 앱 예시 경로(`apps/2048/`, `apps/pixel-art-editor/` 등 `ls apps/`로 확인한 것)를 참고해서 이 블로그의 앱들이 어떤 톤/구조로 만들어졌는지 파악하라는 지시
- `css/style.css`를 읽고 색상 팔레트(CSS 변수)를 spec에 반영하라는 지시
- **사용법 안내 문구**를 앱 어디에 어떻게 넣을지 spec 단계에서부터 설계하라는 지시 (나중에 Build에서 빠뜨리기 쉬움)

spec.md가 나오면 요약해서 사용자에게 보여주고 **명시적 승인**을 받는다. 승인 전에는 Build로 넘어가지 않는다 (`CLAUDE.md`의 "승인 없이 구현을 시작하지 않는다" 규칙). 사용자가 수정을 요청하면 spec.md를 고쳐서 다시 확인받는다.

## 2. Build — 구현 (서브에이전트, 격리)

승인을 받은 뒤에만 진행한다.

1. `assets/build-instructions-template.md`를 바탕으로 저장소 루트에 `build-instructions.md`를 작성한다. spec.md의 요구사항을 요약해 넣고, 아래 "수정 범위" 절을 반드시 포함한다.
2. Agent 도구로 Build 서브에이전트를 새로 띄운다 (Plan 서브에이전트를 재사용하지 않는다 — 서로 다른 서브에이전트여야 범위 오염을 막을 수 있다). `build-instructions.md` 경로를 전달하고 그 지침만 따르게 한다.
3. Build 서브에이전트는 브라우저 테스트를 하지 않는다 — 그건 Review 단계의 몫이다. 구현 후 만든 파일과 핵심 구현 포인트를 보고하게 한다.

**수정 범위 (모든 Build 서브에이전트 지침에 반드시 명시)**:
- `/apps/{{APP_SLUG}}/` 폴더 안의 파일만 새로 만들거나 수정한다.
- 블로그 본체 파일(`index.html`, `css/style.css`, `js/*.js`, `posts/*`, `README.md`, `CLAUDE.md`)은 절대 건드리지 않는다.
- `spec.md`, `build-instructions.md`, `review.md`, `review-instructions.md`도 건드리지 않는다.
- 다른 앱 폴더는 참고용으로 읽기만 하고 수정하지 않는다.

## 3. Review — 검증 (별도 서브에이전트, 필수 분리)

Build 서브에이전트와 **반드시 다른** 서브에이전트를 새로 띄운다. 같은 에이전트가 자기 코드를 검증하면 눈가림 검증이 되기 쉽다.

1. `assets/review-instructions-template.md`를 바탕으로 `review-instructions.md`를 작성한다.
2. Review 서브에이전트에게 실제로 브라우저에서 앱을 켜서(로컬 서버 또는 `run` 스킬/Playwright 등) 핵심 기능이 동작하는지 확인시킨다. 콘솔 에러, 모바일 뷰포트, 다크모드까지 점검한다.
3. 코드 리뷰 항목으로 다음을 **반드시** 포함시킨다 (이 저장소의 웹앱 규칙이라 빠지기 쉬움):
   - 자체 완결: 외부 라이브러리 최소화(CDN은 허용), 블로그 본체 파일 미참조
   - 모바일 대응
   - **색상 팔레트 일치**: `css/style.css`의 CSS 변수 값(`--color-bg`, `--color-text`, `--color-accent` 등)과 앱의 색상이 일치하는지, 다크모드 대응이 되어 있는지
   - **사용법 안내 문구 존재 여부**: 앱 화면 안에서 실제로 눈에 띄게 사용법을 안내하고 있는지 (숨겨져 있거나 누락되면 실패로 처리)
4. 사소한 문제는 Review 서브에이전트가 `/apps/{{APP_SLUG}}/` 범위 내에서 직접 고치게 한다. 구조적으로 큰 문제는 고치지 말고 `review.md`에 기록 후 보고하게 한다.
5. 결과를 `review.md`에 저장한다(이전 리뷰 내용이 있으면 덮어써도 된다).

Review 결과가 "배포 불가"면 Embed로 넘어가지 않고 사용자에게 알린 뒤 필요하면 Build를 다시 돌린다.

## 4. Embed — 블로그에 게시 (직접 수행)

Review를 통과하면 네가 직접 (서브에이전트 없이) 처리한다:

1. `index.html`의 `#app-list` 안에 카드를 하나 추가한다. 기존 카드와 같은 마크업 패턴을 따른다:
   ```html
   <a class="post-card" href="apps/{{APP_SLUG}}/index.html">
     <h3>{{APP_NAME}}</h3>
     <p class="post-summary">{{한 줄 설명}}</p>
   </a>
   ```
2. `git add` / `git commit`으로 새 앱 폴더, `index.html` 변경, `spec.md`/`build-instructions.md`/`review-instructions.md`/`review.md`를 커밋한다. 커밋 메시지는 무엇을 추가했는지 간단히 요약한다.
3. push는 사용자가 명시적으로 요청했을 때만 한다 (일반 git 안전 수칙과 동일).

## 폴더 구조 / 웹앱 규칙 요약

- 모든 웹앱은 `/apps/{앱이름}/` 폴더 안에서 자체 완결된다 (HTML/CSS/JS 전부 그 안에).
- 외부 라이브러리 사용을 최소화한다. CDN은 허용된다.
- 모바일에서도 정상 동작해야 한다.
- **모든 웹앱은 블로그의 색상 팔레트를 따른다.** `css/style.css`의 CSS 변수를 참조해서 앱 자체 `style.css`에 동일한 값을 반영한다 (자체 완결을 지키기 위해 값을 복제하는 것이지, 블로그 stylesheet를 직접 import하는 게 아니다).
- **모든 웹앱에 사용법 안내 문구를 반드시 포함한다.** 화면 어딘가에서 사용자가 바로 확인할 수 있어야 한다.

## 서브에이전트 규칙

- 서브에이전트에게 작업을 넘길 때는 항상 전용 지침 파일(`.md`)을 저장소 루트에 먼저 작성하고, 그 파일 경로를 서브에이전트에게 전달한다 — 프롬프트로만 구두 전달하지 않는다.
- Build 서브에이전트와 Review 서브에이전트는 반드시 분리된 별개의 Agent 호출이어야 한다.
- 서브에이전트는 지침 파일에 명시된 범위만 수정한다. 범위를 벗어나는 게 필요해 보이면 직접 고치지 말고 보고하게 한다.
